# Source consistency and recovery

The database is the durable source authority. A Sandbox VM is a temporary working copy. These are two separate systems, so a successful database commit must not be mistaken for a successful VM application.

## Save protocol

1. The editor submits the revision it loaded. AI generation captures revisions before generation starts. Neither silently adopts a newer baseline at write time.
2. The server-only database transaction checks project ownership and every expected revision, then commits the entire batch. A conflict rejects the whole batch. Identical-content retries are idempotent. Under the same project lock, the existing source trigger also rejects file/directory collisions (for example `src` and `src/page.ts`) across both the batch and previously saved files.
3. The server uploads the committed file contents and returned revisions as a temporary data file. It passes a SHA-256 digest separately to a fixed, isolated Python program in the owned, fixed Sandbox session.
4. That program takes a VM-local lock, checks every file's protected revision journal, and rejects a batch containing an older revision. It journals each accepted revision **before** atomically replacing that file. The API acknowledges the save only after all requested files are confirmed.

The writer uses `Session.cwd`, not an assumed `/vercel/sandbox` path: the current live image reports `/vercel`.

## Failure behavior

| Event | Result |
| --- | --- |
| Stale database revision | HTTP 409; no VM write; editor retains draft |
| New path conflicts with a saved file or directory | HTTP 409 `SOURCE_PATH_CONFLICT`; the entire database batch is rolled back and no VM write starts |
| Restore snapshot contains a file and its descendant | Rejected before VM creation; saved snapshot remains unchanged and export/repair guidance is shown |
| Revision 2 reaches the VM before a delayed revision 1 | Protected journal rejects revision 1; HTTP 409 tells the editor to compare latest |
| Database succeeds but VM upload/application fails | Source remains durable; HTTP 502 provides retry/restore guidance |
| Writer dies after advancing the journal but before file replacement | Older writes stay rejected; retrying the same revision repairs the file |
| Same revision arrives with different content | Rejected; a revision cannot identify two different source contents |
| Snapshot is restored to a replacement VM | New VM journal is populated with the saved database revisions |
| Project/account changes while client work is pending | Requests are cancelled or their results ignored; no adoption by the new account/project |

VM batch application is not a cross-file filesystem transaction. An interrupted batch can be partly applied, but is never reported successful; its committed database contents remain available for retry. Database transactions are not held open across Sandbox network calls.

File/snapshot HTTP reads and JSON bodies now have explicit deadlines, cancellation cleanup and bounded receipts. Snapshot omissions are reported rather than silently treated as a complete copy. See [file API recovery](./file-api-recovery.md) for exact limits and the additional live expiration/ownership checks.

## Trust boundary

- Only the fixed source-management program runs with internal root privileges. No source content is evaluated or interpolated into it; learner/model commands continue through the non-root process guard.
- Python runs with `-I -S` from `/`, so learner-controlled imports and `PYTHONPATH` cannot replace its standard-library modules.
- `/var/lib/codetutor-source-v1` is root-owned and private. Learner code cannot change its lock or revision records.
- Staged data must match the server-provided digest. Changed data is rejected before application.
- Parent directories and targets are accessed without following symlinks. Existing hard-linked/non-regular targets are rejected. Replacement preserves ordinary execute permissions but not setuid/setgid bits.
- Temporary staging paths are generated by the server, outside the source workspace, and cleaned up. Error responses/logs do not include source or raw provider errors.
- SDK calls use a fixed `Session`; automatic resume is not allowed to bypass ownership or sandbox quotas.

## Durable command-source capture

Command reservations now atomically create an owned capture job and source baseline before VM dispatch. A service-only worker claims jobs with expiring, fenced leases; it does not depend on a visible browser or accept a browser-provided sandbox identity. Short post-response work attempts immediate capture. A protected cron route and minute schedule are checked in. Separate sensitive `CRON_SECRET` values are now configured for Vercel Preview/Production and a third local value passes the HTTP authorization smoke check, but **the scheduler is not deployed yet**. Background recovery is therefore not a production guarantee. See [deployment environments](./deployment-environments.md).

The worker scans the fixed sandbox session, reconciles revisions in the database, then acknowledges the durable revision in the VM journal without rewriting source. Lost acknowledgments resume from a durable checkpoint. A command must be observed complete before its final scan; completion during a running scan queues another scan. Background and uncertain commands remain queued with bounded retry rather than holding one request open.

Confirmed journal baselines distinguish applied bytes from pending writes. Unchanged old VM contents cannot overwrite a newer saved version. Deletions use monotonic tombstones; pending/unknown baselines and skipped files are not treated as deletions. A conflicting batch preserves both terminal and saved contents in owner-readable, server-managed conflict records instead of partially saving its siblings.

### Fair scheduling and bounded recovery

Hosted migration `20260827123240_fair_source_capture_scheduling.sql` adds a private account-scheduling ledger. Claims select the least recently served eligible account, then its oldest due job; the later shutdown migration prioritizes due shutdown jobs within that account. At most one capture lease is active per account, including direct post-response dispatches; different accounts can make progress concurrently. Short account/job row locks use `SKIP LOCKED`, and a fresh check after the account lock closes the concurrent-claim race. No transaction waits for VM work. The batch worker still has two lanes, at most ten claim attempts, a 50-second processing deadline and bounded settlement cleanup.

Failures back off from two seconds to a maximum of 60 seconds. Twelve consecutive failures, including abandoned leases, pause the job instead of retrying forever. Paused jobs retain the baseline, capture digest, acknowledgment checkpoint and conflict copies. A malformed claimed payload with a valid lease takes the same bounded failure path; an unconfirmed settlement is not attempted a second time with a conflicting outcome.

**Retry background saves** in Review source posts `{ action: "retry" }` to the owned project's source-recovery endpoint. The server allows three requests per minute and resumes at most ten paused jobs per request, only while their original sandbox is still registered as running and unexpired. It never creates or restarts a VM, resets an active retry cycle, or claims that queued work is already saved. Browser requests are cancelled on unmount/project replacement. Actual background processing still requires deploying the scheduler; this migration alone does not run it.

### Reviewing and resolving source conflicts

The workspace now has a project-scoped **Review source** control. Metadata is paginated (20 records/page); source is fetched only for the selected comparison. Authenticated GET/POST routes under `/api/projects/:projectId/source-recovery` verify project ownership, bound reads/writes, enforce rate limits, reject malformed input and return structured errors. Polling pauses when hidden and stops after a failure until explicit retry. Account changes and unmounts abort obsolete reads and resolutions.

The server-only `resolve_source_conflict` transaction takes the existing project lock, verifies ownership again, and requires the exact current source revision. Choices are keep saved, accept captured content/deletion, or save a manual merge. Competing choices have one winner. Lost receipts replay the original result without writing again, even if source changed later. The original conflict copies and the exact newer saved version reviewed are retained; resolved reviews remain readable and the UI can download both compared copies. Merge drafts survive a comparison reload and require confirmation before closing.

Recapturing the exact same reviewed VM bytes/baseline/session does not recreate an already resolved conflict or override the choice. Changed bytes, baselines or sessions are reviewed again. Saving a resolution does **not** automatically write into a running VM. The status bar reports saved resolutions available for review; this timestamp-based notice is not proof of byte-for-byte VM synchronization.

An explicit **Apply to sandbox** action now reads the resolved content and captured comparison from the authenticated server, not the client. It checks project/sandbox ownership and the exact saved revision before application and rechecks the revision afterward. The fixed VM program acquires the protected command and source locks, refuses a closing workspace or active gated commands (including background preview servers), and replaces a file only if its current digest matches the reviewed capture or the desired contents. A newer or unrelated terminal edit is refused with 409; no saved copy is removed. A root-owned revision journal fences stale applications and allows interrupted writes/deletions to be retried. A successful receipt means that revision was applied at that time, not permanent synchronization.

The originating editor revalidates saved source after application without replacing a newer unsaved draft. Deleted files remain copyable if a draft is open, and a late deletion notification cannot mask a subsequently recreated saved file. Obsolete project/account requests are cancelled. Local filesystem, route, and component tests cover locks, ownership, revised/deleted source, retries, interrupted writes, editor races, and safe failures. The application endpoint now passes the real hosted-VM integration below. Signed-in browser verification and deployment remain release gates.
